# 评测方法与提示词全文

> 这份文档是 WeSchedule 解析链路的**评测说明书**，把自己定的尺子摊开写清楚：
> 语料怎么来的、提示词每一版在改什么、六项指标怎么算、哪些数字能对外说、哪些不能。
> 配套代码：`eval/run_eval.py`（评测脚本）、`cloudfunctions/parse/index.js`（线上实现）。
> 最后更新：2026-10-29（v1.4 修复 T04 缺口：相对周期→期末日规则；另起新语料验证、heldout 保持冻结）

---

## 0. 先说定位

这是一套**回归测试**，不是公开 benchmark。

它的用途只有一个：改提示词之后，判断"变好了还是变坏了"。因此它必须满足两个条件——**可重复**（固定切分、固定种子、温度 0）和**可解释**（分数掉了要能定位到具体哪条消息、哪个字段）。

它不回答"这个解析器有多好"，只回答"这一版比上一版好多少、错在哪"。

## 1. 语料

### 1.1 构成

| 类别 | 条数 | 覆盖什么 | 典型样本 |
|---|---|---|---|
| A 标准表述 | 25 | 日期 + 钟点 + 地点都给全 | "7月24日周五下午3点在主楼A203开班会" |
| B 相对时间 | 20 | 明天/后天/下周X/大后天 | "明天晚上7点老地方打球" |
| C 模糊时间 | 10 | 只有时段词、或完全没有时间 | "晚上有空的话一起自习吧" |
| D 多日程 | 10 | 一条消息里 2–3 件事 | "周日早上跑步，下午图书馆还书，晚上视频会议" |
| E 无日程 | 15 | 闲聊、询问过去、广告、表情 | "哈哈哈哈笑死" |
| F 截止日 | 10 | DDL 表述，无具体钟点 | "作业最晚7月22号交" |
| G 口语碎片 | 10 | 真实群聊腔调、表情、缩写 | "宝子们！！周六志愿活动改到下午两点半了哈" |
| **H 长消息**（2026-10-21 新增） | **12** | 55–128 字、2–5 个事件的群公告，**只进 test** | "【期末考试安排】…7月20日上午9:00-11:00在教二301考《数据结构》；7月22日周三下午2:30…" |
| **R 真实课程群聊**（2026-10-28 新增） | **12** | 用户提供的真实课程群消息（组队 / 截止 / 考试通知），**heldout 冻结集，不进 dev/test、不参与调参** | "请同学们在本周内组好小组并填写成员表格" / "IBA6104 期中考试安排…10月30日14:00–17:00" |
| **合计（dev/test 池）** | **112** | 8:2 切分 → dev 80 / test 32 | |
| **另有 heldout（隔离）** | **12** | 与 dev/test 完全隔离的冻结验证集，见 §5.4 | |
| **另有 relperiod（验证批）** | **6** | 专测「相对周期→期末日」规则（v1.4 新增），见 §5.5 | |

补充事实（据脚本实测，非估计）：

- 语料总事件数 **137** 个（原 97 + 长消息 40），平均文本长度 **27.0 字**，最短 8 字、最长 128 字
- 有日程 97 条、无日程 15 条
- 来源：**构造 105 条 + 真实群聊脱敏 7 条**；另有 **heldout 12 条**（用户提供的真实课程群消息，未参与任何调参）+ **relperiod 6 条**（v1.4 新增的相对周期验证批，不进 dev/test/heldout）
- 切分：8:2 固定，`seed=20260717` → dev 80 / test 32（切分结果落在 `eval/.split.json`，不入库）
- **H 类用 `split_hint: "test"` 钉死在 test 集**，不参与随机切分——否则加语料会把 dev 洗牌，历史数字就不可比了。已验证：加 12 条后原有 100 条的 dev/test 分配一字未变
- **R 类（heldout）用 `split_hint: "heldout"` 钉死**，既不进 dev/test，也通过一个独立的 `--dataset heldout` 通道单独跑。`load_split` 会把它合并进内存里的 split（旧 `.split.json` 不含新条目），但**绝不动 dev/test 的既有分配**——这是"加语料不污染历史数字"的同一套机制。heldout 是"改动时没看过的新语料"，用途只有一个：验证泛化，绝不拿它调参（见 §5 第一条）

### 1.2 为什么这么切分

按条数切而不是按类别切。理由是类别占比本来就不均（A 占 1/4、C 只占 1/10），按类别切会让 test 集出现只有 2–3 条的类别，指标毫无意义。

固定种子是为了**跨版本可比**：v1 和 v1.2 必须跑在完全相同的 80 条上，否则涨跌可能来自换了一批题。

### 1.3 语料怎么改

- 新增/修改条目后加 `--resplit` 会重新生成切分——**不要随便做**，那等于换了考卷，和之前的数字就不能比了
- 改标注必须写清依据（哪条 prompt 规则），并记进提交信息。2026-10-21 改的 10 处就属于这种情况：原标注违反了规则 3/4，改完 dev 从 91.2% 变 95.6%，**这是尺子变准，不是模型变好**
- 语料是公开的（本仓库 `eval/corpus/sample.jsonl`），真实群聊部分已做脱敏，不含人名、群名、手机号

## 2. 提示词

### 2.1 存放与同步

两份**逐字一致**的副本：

| 位置 | 用途 |
|---|---|
| `cloudfunctions/parse/index.js` 的 `SYSTEM_PROMPT` | 线上实际调用 |
| `eval/run_eval.py` 的 `SYSTEM_PROMPT` | 评测调用 |

两边必须同时改。只改一处的话，评测分数不再代表线上表现——这是这套流程最容易犯的错。

版本：`v1.4`（长度 2387 字符）。`ref_date` / `ref_weekday` 在运行时注入。

v1.4 相对 v1.3 只有一处**纯加性**补充，专门修 heldout 暴露的唯一稳定缺口（不动任何既有规则，所以 dev/test 与 v1.3 持平）：

| 改动 | 原本的错 | 改后 |
|---|---|---|
| 规则 5 补「相对周期截止 → 期末日」 | 「本周内组好小组」抽出截止事件但 `date` 永远留空（T04，3/3 稳定复现） | 「本周内→本周日 23:59」「本月内→本月最后一天 23:59」「本季度内→季末 23:59」；若 `ref_date` 已在周期末日取当天 |

v1.3 相对 v1.2 的四处定向修改（每条都先单独复跑 3 次确认稳定）：

| 改动 | 原本的错 | 改后 |
|---|---|---|
| 规则 2 补一句"即使 `ref_date` 正是那个星期几，也要往后推到下一个" | "周五下午2点"在周五当天被算成当天（H005 连续 3 次都错） | 3/3 正确给出下周五 |
| 规则 3 补"明确钟点优先于时段词" | "傍晚六点半"被映射成 18:00，甚至留空（B020 连续 3 次都错） | 3/3 正确给出 18:30 |
| 规则 5 细分截止日的时点 | "下班前"一律 23:59，与原文含义不符 | 下班前→18:00 / 放学前→17:00 / 中午前→12:00 |
| 规则 6 补"排班说明不逐日摊开" | "周一到周三由大一负责"被拆成 5 条事件（多报，事件级查准只有 90.8） | 查准率 98.3 |

### 2.2 全文

```text
你是一个日程信息解析器。用户会给你一段从微信群聊复制的文本，你要判断其中是否包含未来的日程安排，并提取为结构化 JSON。

今天的日期是 {ref_date}，星期{ref_weekday}。所有相对时间都必须以这个日期为锚点换算成绝对日期。

规则：
1. 输出且只输出 JSON，不要输出任何解释、markdown 标记或代码块符号。
2. 相对时间归一化：明天、后天、下周X、X月X日（未给年份时取最近一次的未来日期）都要换算成 YYYY-MM-DD。周X 解析为严格晚于今天（{ref_date}）的下一个匹配星期几（未来向、不含当天），除非文本明确"今天/今/这周X"才取当天。即使 {ref_date} 本身就是文中所说的那个星期几，也必须往后推到下一个——不能因为"今天正好是周五"就把文中的"周五"当成今天。
3. 时段词与模糊时间的区分：
若文本同时给出了时段词和具体钟点（如"傍晚六点半""早上六点"），start_time 必须填那个具体钟点（中文数字也换算成 HH:MM），时段词只作辅助、不要覆盖它，也不要因为两者看似矛盾就留空。
若文本含可映射为具体钟点的时段词且未给具体钟点，则 start_time 取下方映射值、fuzzy_time 填 null：早上/早晨/早自习/第一节课 → 08:00；上午 → 10:00；中午/午间 → 12:00；下午 → 14:00；傍晚 → 17:00；晚上/夜里 → 18:00；第二节课 → 10:00；第三节课 → 14:00。
真正模糊、无法确定钟点的情况（如"有空/大概/左右/最近/哪天都行/找时间/碰一下/再说"等），start_time 填 null，fuzzy_time 填原文表述，confidence 不超过 0.6。
日期填充约束：当消息未指向任何具体某一天（仅模糊时段，或"有空/最近/哪天都行/这周末/下午有会"等），date 必须填 null，禁止填 {ref_date} 或推算日；只有能锚定具体某天（明天/后天/周X/日期/下周X）才填 date。
4. 未明确的时间不要猜测编造。只有原文出现或能直接换算的信息才允许填，否则填 null。
5. 截止日（如"23号前交作业""DDL"）：is_deadline 填 true，reminder_minutes 填 1440。start_time 按时点含义填：只给日期、没有任何时点线索的填 23:59；带明确时点含义的按它填（"下班前"→18:00、"放学前"→17:00、"中午前"→12:00）；"开会前/活动前"这类相对某件事的，指向那件事的开始时间，判断不了填 null。
若截止日用【相对周期】表达（"本周内""这周""本周""本月内""这个月""本季度内"等），date 必须基于 {ref_date} 推算出该周期的最末一天、不能留空：周以【周日】为周期末尾（本周内 → 本周日 23:59）；月 → 本月最后一天 23:59；季度 → 本季度最后一天 23:59；若 {ref_date} 已落在该周期末日，则取当天。start_time 填 23:59，is_deadline 填 true。
6. 一条文本含多个独立日程时，拆成多个 event。但排班、值班、轮值这类说明性安排不要逐日摊开：只有明确指派给"你/我/本人"时才提取一条（date 填起始日，fuzzy_time 填原文的日期范围表述）；"某年级/某组/谁负责"这类泛指不提取。
7. 以下情况 has_schedule 填 false，events 填空数组：纯闲聊寒暄、表情、询问过去的事、广告。注意：只要文本表达了未来的具体行动意图（如自习、开会、办签证、碰毕业论文、约球、聚餐、面试、体检、还书等），即使只有模糊时段（晚上/下午/最近/有空/哪天都行）或未给具体日期，也必须 has_schedule=true 并提取为事件（date 可填 null，fuzzy_time 填原文时段，start_time 填 null）；仅当完全无行动意图才判 false。
8. title 不超过 12 个字，概括事项本身，不要带"请""记得"等语气词。
9. people 只填原文明确出现的参与人，保留原文称呼。
10. location 保留原文最具体的表述，不要补全或推测。
11. confidence 取值 0 到 1，反映你对这条解析整体的把握。字段缺失越多分值越低。
12. 默认提醒：会议和活动 reminder_minutes 填 30，截止日填 1440。

输出 JSON 结构：
{
  "has_schedule": true 或 false,
  "events": [
    {
      "title": "字符串",
      "date": "YYYY-MM-DD",
      "start_time": "HH:MM 或 null",
      "end_time": "HH:MM 或 null",
      "fuzzy_time": "字符串或 null",
      "is_deadline": true 或 false,
      "location": "字符串或 null",
      "people": ["字符串"],
      "reminder_minutes": 数字,
      "confidence": 0 到 1 的数字,
      "raw_snippet": "原文中最相关的一小段"
    }
  ],
  "reject_reason": "has_schedule 为 false 时的一句话原因，否则为 null"
}
```

### 2.3 关键规则的设计意图与代价

**规则 2 —— 周X 取"严格晚于今天"的下一个匹配日（不含当天）**

原文只给"周X"时，有两种读法：当天，或下一个周X。模型没有消息发送时刻，只有 `ref_date`，无法判断"这句话是周五早上说的还是周三说的"。

产品侧的取舍是**宁可往后挪，不可往前放**：这个工具的价值在提醒，解析出一个已经过去的时间，`remind` 会直接判 MISSED，用户等于拿到一条废日程；而往后挪一周，用户在确认页改一次日期就恢复了。**错误方向选择"可修复的那一侧"。**

代价（已知误伤）：周五早上发"周五下午2点答辩"，会被推到下周五，用户要手动改。想彻底解决需要把"当前时刻"也注入提示词（现在是只有日期），那会改动所有相对时间的解析行为，风险大于收益，暂不做。

**规则 3 —— 时段词映射成具体钟点**

"下午"这类词如果不映射，日程就没有具体时间、提醒也就无从计算；映射表的取值（下午=14:00 等）是产品约定，不是客观事实——所以**标注必须和映射表一致**，否则测的是标注噪音。

同时留了一条"真正模糊"的出口：出现"有空/大概/最近"等词时，`start_time` 必须空、`fuzzy_time` 保留原文，不许猜。

**规则 4 —— 不许猜测**

这是"编造率"指标的依据。用户最不容易发现的错，就是模型给他编了一个看起来很合理的钟点。所以评测里专门统计：标注该字段为空、模型却填了值，各计一次。

**规则 7 —— 只要表达了行动意图就必须提取**

早期版本把这些当闲聊丢了（"晚上有空的话一起自习吧"），C 类大量漏报。加这条后 C 类 badcase 清零。

## 3. 六项指标

| 指标 | 定义 | 分母 | 达标线 |
|---|---|---|---|
| `has_schedule` 判定 | 这条消息该不该生成日程（算 P / R / F1） | P：模型判"有"的条数；R：标注判"有"的条数 | F1 目标 100 |
| 误报率 | 15 条无日程样本里被判成"有日程"的比例 | 15 条 E 类 | ≤ 5% |
| 事件级 P / R | 抽出的事件与标注事件逐个配对后的查准 / 查全 | P：模型输出事件数；R：标注事件数（97） | 看趋势，不设线 |
| 字段准确率 | 配对上的事件里 `time` / `location` 与标注完全一致的比例 | **只含配对上的事件** | ≥ 80% / ≥ 70% |
| 整条消息全对率 | 该条消息**所有**标注事件都配上、`time`/`location` 全对、且没有多报 | **只算该有日程的消息**（dev 68 / test 17） | 主指标，不设线 |
| 编造率 | 标注该字段为空、模型却填了值的次数 | 配对上的事件 | 越低越好 |

### 3.1 为什么要专门说明分母

三个容易被误读的地方：

1. **整条全对率的分母不含 15 条闲聊**。它们没有标注事件，判不出"解析对不对"；放进分母等于把它们全部记成失败（早期版本就是这样把 dev 的 60/68 写成 60/80 的）
2. **没有独立的 "date 准确率"**。配对的前提是日期相等，配上了再比日期必然为真——那是恒等于 100% 的伪指标。日期错的代价体现在事件级 P/R 上：配不上就算漏报
3. **`time` 准确率的分母只含配对上的事件**。100% 的意思是"能配上的事件里时间全对"，不是"所有事件时间全对"；配不上的算在事件级召回里

### 3.2 措辞口径（只作诊断，不进主指标）

配对规则对同义改写很苛刻：标注"聚餐"、模型写"一起吃饭"，日期时间全对也判失败。

脚本里有一层保守同义词表（聚餐/吃饭、上课/第X节课、开会/例会/组会、考试、跑步），并且强制"预答辩 ≠ 正式答辩"。放宽后：**dev 98.5%（67/68）· test 100%（17/17）**。

**这个数不用来当成绩**：同义词表由我定义，哪些改写算同一件事没有客观标准，拿它对外等于自定规则自己打分。它唯一的用途是回答"剩下的错是没理解，还是只是换了个说法"。

### 3.3 这套样本能分辨多大的差别

100 条听起来不少，但落到"通过率"这个比例上，样本量决定了它能说多细。按 Wilson 区间算（95% 置信度）：

| 样本 | 通过率 | 95% 置信区间 | 区间宽度 |
|---|---|---|---|
| dev 66/68（v1.3） | 97.1% | 89.9%–99.2% | 9.3pp |
| test 28/29（v1.3） | 96.6% | 82.8%–99.4% | 16.6pp |

反过来说：要在 95% 置信度下把精度做到 **±5pp，大约需要 73 条**；**±3pp 约需 203 条**；**±2pp 约需 457 条**。

所以正确的读法是：

- **判断"这版比上版好还是坏"——够用**。同一批题、同一天、同一模型版本下做配对比较，能分辨 2 条（约 3pp）以上的差异
- **对外报"准确率 95.6%"——不够精确**。真实值落在 88%–98% 这个区间里，写"95.6%"只是这次抽样的点估计
- **想覆盖更多场景——不是加条数，是加场景**。2026-10-21 补的 12 条长消息把 test 从 94.1% 拉低到 89.7%，说明原来的 100 条严重低估了长消息的失败率；这比再加 100 条同类短消息有价值得多

## 4. 复现

```bash
pip install requests
export DEEPSEEK_API_KEY=sk-xxxx        # Windows: set DEEPSEEK_API_KEY=sk-xxxx

python eval/run_eval.py --dataset dev
python eval/run_eval.py --dataset test
python eval/run_eval.py --dataset heldout      # 真实课程群聊冻结集（不调参）
python eval/run_eval.py --dataset relperiod    # 相对周期规则验证集（v1.4 新增）
python eval/verify_relperiod.py                # 相对周期规则稳定性：每条 3 次复跑
```

或用 `eval/run_dev.sh`（Windows: `run_dev.bat`）自动读取项目根 `.env`。

成本：dev 80 条，每条最多 2 次调用（校验失败会重试 1 次），单条约 1–3 秒。一次全量 dev 约 1.5 分钟。

输出：控制台打印六项指标 + badcase 数量；逐条 badcase 落到 `eval/reports/badcase_<prompt>_<dataset>.jsonl`（不入库）。

## 5. 已知局限

| 局限 | 影响 |
|---|---|
| **v1.3 的 test 集已被污染** | 这轮我是看着 badcase 改提示词的，而其中 H005 / H007 属于 test 集。改完再在同一批题上验证，**等于既出题又对答案**——96.6% 这个数带乐观偏差。test 本该是"只看不改"的验收集，现在不是了。**补救：2026-10-28 新增 12 条真实课程群聊作 heldout 冻结集（改动时没看过），专门验泛化、绝不调参**（见 §5.4） |
| 语料 105/112（dev/test 池）是构造的 | 验证的是"我预想到的问题有没有被修掉"，不代表真实流量分布。**heldout 12 条是真实课程群消息**，弥补了这一点，但样本仍小（见 §5.4） |
| 标注、指标、口径都是自定 | 数字不能与公开 benchmark 类比 |
| 整条全对的判定很硬 | 任一字段不一致就整条失败，比"能不能用"严格 |
| **排班 / 值班类说明的处理未定义** | 例如"周一到周三由大一负责"。它算不算"我的日程"、要不要逐日拆成事件，没有统一口径。长消息 H002 的失败正落在这：模型把它拆成 5 条逐日事件，标注一条都不算——**这条 badcase 的性质是"口径未定义"，不是"模型错了"** |
| "下班前"这类表述未定义钟点 | 规则 5 要求 DDL 未给时间填 23:59，但"下班前"更像 18:00。H012 模型给 18:00、标注写 23:59，两边都讲得通 |
| 长消息样本量小 | H 类只有 12 条，只能说明"长消息是弱项"，说不出弱到什么程度 |
| 模型本身不可控 | `temperature=0` 也不逐字可复现；100 条语料分辨率约 ±2 条（±3pp） |
| 无线上回流 | 评测集离线固定，尚未把线上 `parse_logs` 接进闭环 |

### 5.4 heldout 真实验证集（2026-10-28）

12 条**用户提供的真实课程群聊**（组队 / 截止 / 考试 / Quiz 通知），gold 严格按 prompt 契约标注；`ref_date` 为按内容推断的发送日（已逐条标注依据）。`split_hint: "heldout"` 钉死，**不进 dev/test、不参与任何调参**——它是"改动时没看过"的集，用途只有一个：验证泛化。

结果（prompt v1.3，单跑 + 单条 3 次复跑确认稳定性）：

| 指标 | 值 | 说明 |
|---|---|---|
| `has_schedule` 判定 | **100%（0 误报）** | 3 条无日期公告（表格已上传 / 链接已开放 / 提交要求）模型正确沉默——**泛化到真实场景没有过度抽取**，这是比"通过率"更值钱的信号 |
| 整条消息全对率 | **稳定期望 8/9（约 88.9%）** | 单次采样在 7/9–8/9 间波动（T01/T11 偶发掉字段，已 3 次复跑确认稳定可修）；仅剩 T09 中英标题措辞、T11 时间 flaky 两项非解析错 |
| 事件级 P / R | 77.8% / 77.8% | |
| `time` / `location` 准确率 | **100% / 100%** | 抽到的都对；编造 0 |
| 误报率 | 0% | |

剩余失败的性质（v1.3 单跑时；**T04 已在 v1.4 修复，见 §5.5**）：

- **T04「请同学们在本周内组好小组并填写成员表格」= 已在 v1.4 修复**：v1.3 下 3/3 抽出截止事件（`is_deadline=true`）但 `date` 永远留空——规则 5 未定义"本周内 → 期末日"。v1.4 给规则 5 补了相对周期子规则后，T04 在定向 3 次复跑中 3/3 给出「本周日 23:59」，heldout 两次聚合采样也均在通过集内。
- **T09「Group Formation 明天 11:59pm 截止」= 仅标题中英措辞不同**：日期（2026-10-22）、时间（23:59）、截止标志全对；模型把标题写成"小组组建合同提交"，gold 用英文源词。属于评测匹配盲点（中英无翻译同义词），不是模型解析错。
- **T11「今天的 Quiz 会在 16:30 结束并关闭通道」= 边界表述不稳定**：`date` 每次都对（2026-10-22），`start_time` 1/3 抽到 16:30、2/3 留空——是"日期稳定、时间 flaky"的边界 case，不是稳定漏抽。

**结论**：v1.3 在真实学术场景上泛化良好——相对时间（今天/明天/今晚）、带具体日期+时间+地点的考试、单条截止全对，**且对纯公告零误报**。唯一稳定可修的缺口是"相对周期 → 期末日"，已在 v1.4 修复（见 §5.5、§6）。

⚠️ **纪律约束**：heldout 是"改动时没看过"的集，发现 T04 缺口后**没有**在 heldout 上改 prompt 再验（那会重演 test 污染）。任何修复必须用**另一批新语料**验证，heldout 保持冻结。

### 5.5 相对周期规则验证集 relperiod（2026-10-29，v1.4 新增）

为验证 T04 缺口的修复**不在 heldout 上回测**（守住上一条纪律），另建一批新语料 `eval/corpus/relative_period.jsonl`（6 条，`split_hint: "relperiod"`），覆盖「本周内 / 本月内 / 本季度内 / 这周内」+ 一个周日边界（ref 已是周日 → 取当天）+ 一个绝对日期对照（10月25日前）。gold 的期末日由脚本从 `ref_date` 推算，避免手算错。

用 `eval/verify_relperiod.py` 每条**复跑 3 次**确认稳定性（我们立的方法：单条 3 次定稳定性，比单次聚合可靠）：

| 用例 | ref_date | 期望 date | 3 次结果 |
|---|---|---|---|
| R01 本周内组小组 | 2026-10-14 | 2026-10-18（周日） | 3/3 ✓ |
| R02 本月内交综述 | 2026-10-14 | 2026-10-31（月末） | 3/3 ✓ |
| R03 本季度内交初稿 | 2026-10-14 | 2026-12-31（季末） | 3/3 ✓ |
| R04 本周内交报销（ref=周日） | 2026-10-18 | 2026-10-18（当天） | 3/3 ✓ |
| R05 这周内发周报 | 2026-11-03 | 2026-11-08（周日） | 3/3 ✓ |
| R06 10月25日前（对照） | 2026-10-14 | 2026-10-25（绝对日期） | 3/3 ✓ |

**总命中 18/18（6 条 × 3 次）**。修复泛化成立：规则对周 / 月 / 季度三类相对周期、周日边界、以及绝对日期对照均无回归。

⚠️ 纪律复盘：T04 是 heldout 里发现的，验证修复**用另一批语料**（relperiod），heldout 保持冻结。heldout 两次聚合采样（v1.4）均显示 T04 在通过集内，但那只是旁证；主证据是上面的 relperiod 18/18。
