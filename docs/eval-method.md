# 评测方法与提示词全文

> 这份文档是 WeSchedule 解析链路的**评测说明书**，把自己定的尺子摊开写清楚：
> 语料怎么来的、提示词每一版在改什么、六项指标怎么算、哪些数字能对外说、哪些不能。
> 配套代码：`eval/run_eval.py`（评测脚本）、`cloudfunctions/parse/index.js`（线上实现）。
> 最后更新：2026-10-21（标注口径统一 + 同义词诊断）

---

## 0. 先说定位

这是一套**回归测试**，不是公开 benchmark。

它的用途只有一个：改提示词之后，判断"变好了还是变坏了"。因此它必须满足两个条件——**可重复**（固定切分、固定种子、温度 0）和**可解释**（分数掉了要能定位到具体哪条消息、哪个字段）。

它不回答"这个解析器有多好"，只回答"这一版比上一版好多少、错在哪"。

## 1. 语料

### 1.1 构成

| 类别 | 条数 | 覆盖什么 | 典型样本 |
|---|---|---|---|
| A 标准表述 | 25 | 日期 + 钟点 + 地点都给全 | "7月24日周五下午3点在主楼A203开班会" |
| B 相对时间 | 20 | 明天/后天/下周X/大后天 | "明天晚上7点老地方打球" |
| C 模糊时间 | 10 | 只有时段词、或完全没有时间 | "晚上有空的话一起自习吧" |
| D 多日程 | 10 | 一条消息里 2–3 件事 | "周日早上跑步，下午图书馆还书，晚上视频会议" |
| E 无日程 | 15 | 闲聊、询问过去、广告、表情 | "哈哈哈哈笑死" |
| F 截止日 | 10 | DDL 表述，无具体钟点 | "作业最晚7月22号交" |
| G 口语碎片 | 10 | 真实群聊腔调、表情、缩写 | "宝子们！！周六志愿活动改到下午两点半了哈" |
| **合计** | **100** | | |

补充事实（据脚本实测，非估计）：

- 语料总事件数 **97** 个，平均文本长度 **20.2 字**，最短 8 字、最长 39 字
- 有日程 85 条、无日程 15 条
- 来源：**构造 93 条 + 真实群聊脱敏 7 条**
- 切分：8:2 固定，`seed=20260717` → dev 80 / test 20（切分结果落在 `eval/.split.json`，不入库）

### 1.2 为什么这么切分

按条数切而不是按类别切。理由是类别占比本来就不均（A 占 1/4、C 只占 1/10），按类别切会让 test 集出现只有 2–3 条的类别，指标毫无意义。

固定种子是为了**跨版本可比**：v1 和 v1.2 必须跑在完全相同的 80 条上，否则涨跌可能来自换了一批题。

### 1.3 语料怎么改

- 新增/修改条目后加 `--resplit` 会重新生成切分——**不要随便做**，那等于换了考卷，和之前的数字就不能比了
- 改标注必须写清依据（哪条 prompt 规则），并记进提交信息。2026-10-21 改的 10 处就属于这种情况：原标注违反了规则 3/4，改完 dev 从 91.2% 变 95.6%，**这是尺子变准，不是模型变好**
- 语料是公开的（本仓库 `eval/corpus/sample.jsonl`），真实群聊部分已做脱敏，不含人名、群名、手机号

## 2. 提示词

### 2.1 存放与同步

两份**逐字一致**的副本：

| 位置 | 用途 |
|---|---|
| `cloudfunctions/parse/index.js` 的 `SYSTEM_PROMPT` | 线上实际调用 |
| `eval/run_eval.py` 的 `SYSTEM_PROMPT` | 评测调用 |

两边必须同时改。只改一处的话，评测分数不再代表线上表现——这是这套流程最容易犯的错。

版本：`v1.2`（长度 1804 字符）。`ref_date` / `ref_weekday` 在运行时注入。

### 2.2 全文

```text
你是一个日程信息解析器。用户会给你一段从微信群聊复制的文本，你要判断其中是否包含未来的日程安排，并提取为结构化 JSON。

今天的日期是 {ref_date}，星期{ref_weekday}。所有相对时间都必须以这个日期为锚点换算成绝对日期。

规则：
1. 输出且只输出 JSON，不要输出任何解释、markdown 标记或代码块符号。
2. 相对时间归一化：明天、后天、下周X、X月X日（未给年份时取最近一次的未来日期）都要换算成 YYYY-MM-DD。周X 解析为严格晚于今天（{ref_date}）的下一个匹配星期几（未来向、不含当天），除非文本明确"今天/今/这周X"才取当天。
3. 时段词与模糊时间的区分：
若文本含可映射为具体钟点的时段词且未给具体钟点，则 start_time 取下方映射值、fuzzy_time 填 null：早上/早晨/早自习/第一节课 → 08:00；上午 → 10:00；中午/午间 → 12:00；下午 → 14:00；傍晚 → 17:00；晚上/夜里 → 18:00；第二节课 → 10:00；第三节课 → 14:00。
真正模糊、无法确定钟点的情况（如"有空/大概/左右/最近/哪天都行/找时间/碰一下/再说"等），start_time 填 null，fuzzy_time 填原文表述，confidence 不超过 0.6。
日期填充约束：当消息未指向任何具体某一天（仅模糊时段，或"有空/最近/哪天都行/这周末/下午有会"等），date 必须填 null，禁止填 {ref_date} 或推算日；只有能锚定具体某天（明天/后天/周X/日期/下周X）才填 date。
4. 未明确的时间不要猜测编造。只有原文出现或能直接换算的信息才允许填，否则填 null。
5. 截止日（如"23号前交作业""DDL"）：is_deadline 填 true，未给具体时间时 start_time 填 23:59，reminder_minutes 填 1440。
6. 一条文本含多个独立日程时，拆成多个 event。
7. 以下情况 has_schedule 填 false，events 填空数组：纯闲聊寒暄、表情、询问过去的事、广告。注意：只要文本表达了未来的具体行动意图（如自习、开会、办签证、碰毕业论文、约球、聚餐、面试、体检、还书等），即使只有模糊时段（晚上/下午/最近/有空/哪天都行）或未给具体日期，也必须 has_schedule=true 并提取为事件（date 可填 null，fuzzy_time 填原文时段，start_time 填 null）；仅当完全无行动意图才判 false。
8. title 不超过 12 个字，概括事项本身，不要带"请""记得"等语气词。
9. people 只填原文明确出现的参与人，保留原文称呼。
10. location 保留原文最具体的表述，不要补全或推测。
11. confidence 取值 0 到 1，反映你对这条解析整体的把握。字段缺失越多分值越低。
12. 默认提醒：会议和活动 reminder_minutes 填 30，截止日填 1440。

输出 JSON 结构：
{
  "has_schedule": true 或 false,
  "events": [
    {
      "title": "字符串",
      "date": "YYYY-MM-DD",
      "start_time": "HH:MM 或 null",
      "end_time": "HH:MM 或 null",
      "fuzzy_time": "字符串或 null",
      "is_deadline": true 或 false,
      "location": "字符串或 null",
      "people": ["字符串"],
      "reminder_minutes": 数字,
      "confidence": 0 到 1 的数字,
      "raw_snippet": "原文中最相关的一小段"
    }
  ],
  "reject_reason": "has_schedule 为 false 时的一句话原因，否则为 null"
}
```

### 2.3 关键规则的设计意图与代价

**规则 2 —— 周X 取"严格晚于今天"的下一个匹配日（不含当天）**

原文只给"周X"时，有两种读法：当天，或下一个周X。模型没有消息发送时刻，只有 `ref_date`，无法判断"这句话是周五早上说的还是周三说的"。

产品侧的取舍是**宁可往后挪，不可往前放**：这个工具的价值在提醒，解析出一个已经过去的时间，`remind` 会直接判 MISSED，用户等于拿到一条废日程；而往后挪一周，用户在确认页改一次日期就恢复了。**错误方向选择"可修复的那一侧"。**

代价（已知误伤）：周五早上发"周五下午2点答辩"，会被推到下周五，用户要手动改。想彻底解决需要把"当前时刻"也注入提示词（现在是只有日期），那会改动所有相对时间的解析行为，风险大于收益，暂不做。

**规则 3 —— 时段词映射成具体钟点**

"下午"这类词如果不映射，日程就没有具体时间、提醒也就无从计算；映射表的取值（下午=14:00 等）是产品约定，不是客观事实——所以**标注必须和映射表一致**，否则测的是标注噪音。

同时留了一条"真正模糊"的出口：出现"有空/大概/最近"等词时，`start_time` 必须空、`fuzzy_time` 保留原文，不许猜。

**规则 4 —— 不许猜测**

这是"编造率"指标的依据。用户最不容易发现的错，就是模型给他编了一个看起来很合理的钟点。所以评测里专门统计：标注该字段为空、模型却填了值，各计一次。

**规则 7 —— 只要表达了行动意图就必须提取**

早期版本把这些当闲聊丢了（"晚上有空的话一起自习吧"），C 类大量漏报。加这条后 C 类 badcase 清零。

## 3. 六项指标

| 指标 | 定义 | 分母 | 达标线 |
|---|---|---|---|
| `has_schedule` 判定 | 这条消息该不该生成日程（算 P / R / F1） | P：模型判"有"的条数；R：标注判"有"的条数 | F1 目标 100 |
| 误报率 | 15 条无日程样本里被判成"有日程"的比例 | 15 条 E 类 | ≤ 5% |
| 事件级 P / R | 抽出的事件与标注事件逐个配对后的查准 / 查全 | P：模型输出事件数；R：标注事件数（97） | 看趋势，不设线 |
| 字段准确率 | 配对上的事件里 `time` / `location` 与标注完全一致的比例 | **只含配对上的事件** | ≥ 80% / ≥ 70% |
| 整条消息全对率 | 该条消息**所有**标注事件都配上、`time`/`location` 全对、且没有多报 | **只算该有日程的消息**（dev 68 / test 17） | 主指标，不设线 |
| 编造率 | 标注该字段为空、模型却填了值的次数 | 配对上的事件 | 越低越好 |

### 3.1 为什么要专门说明分母

三个容易被误读的地方：

1. **整条全对率的分母不含 15 条闲聊**。它们没有标注事件，判不出"解析对不对"；放进分母等于把它们全部记成失败（早期版本就是这样把 dev 的 60/68 写成 60/80 的）
2. **没有独立的 "date 准确率"**。配对的前提是日期相等，配上了再比日期必然为真——那是恒等于 100% 的伪指标。日期错的代价体现在事件级 P/R 上：配不上就算漏报
3. **`time` 准确率的分母只含配对上的事件**。100% 的意思是"能配上的事件里时间全对"，不是"所有事件时间全对"；配不上的算在事件级召回里

### 3.2 措辞口径（只作诊断，不进主指标）

配对规则对同义改写很苛刻：标注"聚餐"、模型写"一起吃饭"，日期时间全对也判失败。

脚本里有一层保守同义词表（聚餐/吃饭、上课/第X节课、开会/例会/组会、考试、跑步），并且强制"预答辩 ≠ 正式答辩"。放宽后：**dev 98.5%（67/68）· test 100%（17/17）**。

**这个数不用来当成绩**：同义词表由我定义，哪些改写算同一件事没有客观标准，拿它对外等于自定规则自己打分。它唯一的用途是回答"剩下的错是没理解，还是只是换了个说法"。

## 4. 复现

```bash
pip install requests
export DEEPSEEK_API_KEY=sk-xxxx        # Windows: set DEEPSEEK_API_KEY=sk-xxxx

python eval/run_eval.py --dataset dev
python eval/run_eval.py --dataset test
```

或用 `eval/run_dev.sh`（Windows: `run_dev.bat`）自动读取项目根 `.env`。

成本：dev 80 条，每条最多 2 次调用（校验失败会重试 1 次），单条约 1–3 秒。一次全量 dev 约 1.5 分钟。

输出：控制台打印六项指标 + badcase 数量；逐条 badcase 落到 `eval/reports/badcase_<prompt>_<dataset>.jsonl`（不入库）。

## 5. 已知局限

| 局限 | 影响 |
|---|---|
| 语料 93/100 是构造的 | 验证的是"我预想到的问题有没有被修掉"，不代表真实流量分布 |
| 标注、指标、口径都是自定 | 数字不能与公开 benchmark 类比 |
| 整条全对的判定很硬 | 任一字段不一致就整条失败，比"能不能用"严格 |
| 模型本身不可控 | `temperature=0` 也不逐字可复现；100 条语料分辨率约 ±2 条（±3pp） |
| 长消息未覆盖 | 现有语料平均 20 字，30–200 字的群公告（多事件长文本）完全没测 |
| 无线上回流 | 评测集离线固定，尚未把线上 `parse_logs` 接进闭环 |
