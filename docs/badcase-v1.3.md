> 完整运行产物在 `eval/reports/badcase_<prompt>_<dataset>.jsonl`（本地生成、不入库），

## 2. v1.3 修掉的四个问题（都有复跑证据）

v1.2 那一轮有 6 条失败，其中 3 条不是措辞问题，改法是给提示词补四条定向规则。**每条改完都单独复跑 3 次**，确认不是抽样运气：

| 问题 | 改前表现（3 次复跑） | 改法 | 改后 |
|---|---|---|---|
| H005「周五下午2点」在周五当天被算成当天 | 3/3 全错 | 规则 2 补：即使 `ref_date` 正是那个星期几，也要往后推 | 3/3 正确 → 下周五 |
| B020「傍晚六点半」被映射成 18:00，甚至留空 | 3/3 全错（1 次 18:00、2 次 null） | 规则 3 补：明确钟点优先于时段词，不许留空 | 3/3 正确 → 18:30 |
| H002「周一到周三由大一负责」被拆成 5 条值班事件 | 稳定（每条长消息都拆） | 规则 6 补：排班/值班说明不逐日摊开，泛指主体不提取 | 不再拆，事件级查准 90.8 → 98.3 |
| H012「下班前」被标成 23:59 | 稳定 | 规则 5 细分：下班前 → 18:00、放学前 → 17:00、中午前 → 12:00 | time 准确率 98.1% → 100% |

**为什么 D007 没有跟着一起改**：它的表现是"周五算成当天"，和 H005 同类，但**单独复跑 3 次全部正确**——属于波动而非稳定错误。后来加了规则 2 的补丁，D007 也顺带稳定了，但当时没有为它单独动过提示词。这条留作经验：**单条 badcase 先跑 3 次，再决定要不要改 prompt**。

## 4. 怎么复核这张表

```bash
python eval/run_eval.py --dataset dev     # 重新生成 reports/badcase_v1.3_dev.jsonl
python eval/run_eval.py --dataset test
```

重跑得到的是**新一次采样**，条数可能与本文差 ±2（见 `docs/eval-method.md` §5）。

## 5. 结论

1. **失败面已经收敛到"配对口径"这一层**：剩下 3 条日期时间全对，只是标题写法不同
2. **继续在评分上做文章没有意义**——把同义词表放宽就能到 100%，但那是改尺子不是改模型
3. **真正该做的是补一批没看过的新语料**：现在的 test 被调参污染过，新数据才能验证 v1.3 的改动是不是真的泛化
4. 方法上的收获：**小样本下看总数判断不了改动好坏（±2 条噪声），要看单个失败项复跑后的稳定性**
